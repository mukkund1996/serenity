# 0049 · `@copy` and `@handover`: a session writes a handover doc, which starts a follow-up session or goes to Slack as a file

**Status:** Accepted · 2026-10-30 · Builds on 0048, 0032, 0030

## Context
The context a session builds up stays in its agent: why a decision was made, what is half done, which PR holds what. Continuing that work in a fresh session, or handing it to a teammate, means writing it down, and the agent that did the work is best placed to do that. The master could ask it with `send_reply` and `watch_session`, but then the doc's text would come back as scraped reply text. Its location would be whatever the agent picked, and it would be gone once the worktree is cleaned up.

## Decision
- **Two commands** (0048's `MASTER_COMMANDS`): `@copy @session <follow-up>` and `@handover @session`. Each adds a note to the user's message that tells the master which tool to call.
- **The doc is written in the worktree, then copied into serenity's state.** A new master tool, `request_handover` (`session`, `purpose` copy or share, `for`), types a fixed request into the session's agent. It asks the agent to write `<cwd>/.serenity/handover.md` with Goal, State, Decisions, Open questions, Key files/branches/PRs and Next steps (for the follow-up, with `@copy`). Writing inside its own worktree needs no extra permission. serenity first creates `.serenity/` with a `.gitignore` of `*`, so git ignores it, and removes an old doc so it can't pass for the new one. The tool sets a watch (0032) on the session. When the session's turn ends, serenity copies a doc written since the request to `<home>/handovers/<repo>/<session>-<UTC stamp>.md`, which outlives the worktree. It records the copy in the master's record and tells the chat the path. If no new doc was written, it tells the chat that instead. A session asked while it was working gets one more turn, because the turn it was in may end before it reads the request.
- **The gate is the command.** `request_handover` runs only when the user's latest message has `@copy` (for copy) or `@handover` (for share) and @-mentions that session, the same proof as a mention (0036). The session must be able to take input, as for `send_reply`.
- **`@copy` starts the follow-up at once.** Once the doc is ready, serenity's message tells the master to call `create_session` with a new name, a prompt for the follow-up, and `handover` set to the doc's path. The daemon then appends the doc to the prompt itself (`<handover>…</handover>`), so the doc reaches the new agent word for word. `handover` accepts only a path serenity copied, so no other file can be fed to an agent this way. The new session gets its own worktree off the default base, like any `create_session`.
- **`@handover` reuses an up-to-date doc.** A copied doc counts as up to date while the session is not working and its last reply is the same as when the doc was copied. Otherwise the session is asked again. The master gives the user the path, and reads the doc if they ask what it says.
- **Sharing on Slack as a file.** Slack's MCP server uploads in two steps: `slack_get_file_upload_url`, then a POST of the raw bytes, then `slack_complete_file_upload`. The chat can't POST, and the token belongs to the `claude` CLI (0023). A new master tool, `share_slack_file` (`path`, `channel_id`, `thread_ts`, `comment`), therefore runs a one-shot worker allowed only the URL tool, POSTs the bytes from the daemon, and runs a second worker allowed only the complete tool, with the comment passed verbatim between markers. A URL that gets a 401 is fetched once more. Only handover docs serenity copied can be shared, and only to a channel, DM or group DM ID (`C…`, `D…`, `G…`).
- **Shares need the user's confirmation, as messages do (0030).** `share_slack_file` runs only when the user's latest message answers a master reply that showed the file name, the channel ID and the comment. Anything else is refused and the master is told to draft and ask. A share is never sent through NEEDS YOU.

## Consequences
- A handover costs the session one turn, which the user sees on the map. A session waiting on a permission prompt can't be asked until the user answers it.
- Freshness is a heuristic: a session that changed files without replying again looks up to date. `@copy` always asks for a new doc.
- The upload URL passes through a model's JSON output, and the tool's own docs warn that a retyped URL breaks. The https check and the one retry limit the damage, but a share can still fail with "Slack refused the upload". The bytes never pass through a model.
- A person with no existing DM can't be reached: opening a DM is a write the master doesn't have. The master asks for a channel instead.
- Docs pile up under `handovers/`, one per request; nothing deletes them yet.
