# 0063 · Renaming checks its name in the dialog; `@move @session <topic>` moves sessions, and `set_topic` waits like any move

**Status:** Accepted · 2026-11-05 · Amends 0047, 0048

## Context
`r` already renamed a session: a dialog over the map, the `session.rename` RPC, and `Daemon.rename`, which also renames the tmux window of a session serenity started. A check end to end found it working: the dialog opens on a card in both zooms and on a session's NEEDS YOU row, Esc closes it, the name is stored (so it survives a daemon restart), the summarizer never writes names, and the map and the `@` list show the new name on the next broadcast. The gaps were small:
- The rules lived only in the daemon (`freeName`). The dialog learned of a bad name only from the RPC's error, and nothing tested the rules.
- A clash was exact-case: `API-auth` could sit beside `api-auth`. The two look the same in the `@` list, and on a case-insensitive filesystem they can't both have a worktree.
- The dialog didn't say what a rename leaves alone.

Moving sessions between topics had one path, asking the master in words. It then called `set_topic`, which moved at once even while the session worked or the user typed. 0047 made that an exception to its rule that moves wait so a card doesn't jump under the user.

## Decision
- **One set of name rules, in core.** `checkSessionName(raw, sessions, self?)` (`session-name.ts`) turns spaces into `-`. It then requires `NAME_PATTERN` (letters, digits, `. _ -`, not leading with `. _ -`, at most 40), refuses a command word in any case (0048, now `new`, `copy`, `handover` and `move`), and refuses a name another session holds, **in any case**. A session holds its name unless it is archived, or ended and not pinned. A session may keep its name or change only its case. The daemon's `freeName` (create and rename) and the rename dialog both use it. The dialog checks on Enter and shows the error in place; the daemon checks again.
- **What a rename changes.** The map's name, and the tmux window of a session serenity started (an attached one when it's parked again). The branch and worktree keep their names: renaming a branch with an open PR or a pushed upstream would break the PR link (0055) and the user's other clones, and moving a worktree under a running agent would pull its cwd away. The dialog says so: "renames its tmux window too" (or "its tmux window keeps its name: it is yours" for an imported one) and "branch <branch> and its worktree keep their names".
- **Where `r` works.** On a card in the topics and map zooms, and on a session's row in NEEDS YOU. In the session zoom the keys belong to the agent; `Ctrl+q` back to the map first.
- **`@move` is a command word.** `MASTER_COMMANDS.move` = "move sessions to a topic". It is reserved as a name, offered first in the `@` list with its hint, and coloured **cyan**. That keeps it apart from a session's `blueBright`, `@new`'s green, `@copy` and `@handover`'s yellow, and the master's own magenta.
- **serenity reads the request, the master acts.** `parseMove(text, sessions)` (`mentions.ts`) returns every live session the message @-mentions (once each, in order), the `@word`s that name no live session, and the topic. The topic is the first text after `@move` that is more than what joins the mentions (`,`, `and`, `&`), up to a clause break (`, ; ! ?`, a sentence's full stop, a new line). A leading "to", "into", "under", "in" or "the", a trailing "topic" and quotes are dropped. `chatMessage` adds a note built from it (`moveNote`). With sessions and a topic that fits, it says: call `set_topic` now, once per session, with this topic and no question first. It also says whether the topic exists, is a near-duplicate of one (`capTopic`, 0047), or is new. It counts the topics left once these sessions leave theirs, so a topic the move empties doesn't count. When a new topic would pass `maxTopics`, the note says to call nothing and to tell the user, naming the topics there are. With no topic, ask which; with no live session, say how to use it. Unknown names are reported. Either way, the chat confirms in one sentence what moved, what waits and what was refused.
- **`set_topic` waits like any move (amends 0047).** A move asked for by the user, in words or by `@move`, now follows the same rule as the summarizer's: while the session is `working`, or while the user types in any of the repo's maps, the move is stored in `topicHeld` and made when that stops. The cap is checked again then; a held move that no longer fits is dropped and logged. The result says which happened ("api-auth is working: it moves to release once it stops."), and the chat passes it on. A move to where the session already is cancels a held one. `create_session`'s `topic` still applies at once: a new card has nowhere to jump from.
- **The master's skill** has an "@move" section and a line on renames: only the user renames, and the next snapshot has the new name.

## Consequences
- A session named `move` from before this change keeps its name but can't be `@`-mentioned until renamed (as 0048 set out for any new command word). A new name that differs from a live one only in case is refused where it was allowed before.
- An `@move` of a working session confirms "moves once it stops", not "moved". A move asked for in words behaves the same, which it didn't before.
- The topic parse is heuristic. A message that puts other words before the topic ("@move @a over to the release topic please") leaves the extra words in, and the topic is then a new, odd name. The note quotes the topic it read, so the master's confirmation shows it, and another `@move` fixes it.
- A held `@move` stays held until the session's turn ends. A summary proposing its old topic twice in a row in the meantime moves it back, as it could after an immediate move.
